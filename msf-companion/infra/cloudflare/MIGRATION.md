### DNS records

Cloudflare's scanner imported 21 records and **set every CNAME to proxied**,
which is wrong for service-discovery and mail-authentication records. Proxying a
DKIM CNAME makes it answer with Cloudflare IPs instead of returning the target,
so DKIM signing fails and mail starts landing in spam. Eight records were
corrected to DNS-only:

| Record | Purpose | Why it must be DNS-only |
| --- | --- | --- |
| `s1._domainkey`, `s2._domainkey` | SendGrid DKIM | Proxying breaks DKIM signing |
| `autodiscover`, `msoid` | Microsoft 365 mailbox autoconfiguration | Clients need the real target |
| `lyncdiscover`, `sip` | Teams/Skype discovery and signalling | Non-HTTP protocols |
| `email` | GoDaddy webmail | Non-proxied host |
| `_domainconnect` | GoDaddy automated setup | Must resolve to GoDaddy |

Only the root `A` record (→ `20.66.70.23`, the Azure Container Apps origin) and
`www` remain proxied. That is the Phase 0 benefit: CDN, WAF, bot protection and
analytics in front of an otherwise unchanged Azure origin.

> **Pre-existing mail problem, unrelated to this migration.** The root SPF record
> is `v=spf1 include:secureserver.net -all` (GoDaddy only), but the root MX
> points at Outlook and there are DKIM keys for both SendGrid and Resend. Mail
> sent from `@themsftoolkit.com` through any of those three fails SPF against a
> hard `-all`. This is live today on Azure and should be fixed under its own

## 2. Phase 1 — the web app on Cloudflare Containers

### What is in the repo

| File | Role |
| --- | --- |
| `msf-companion/wrangler.jsonc` | Worker + container + Durable Object config. **No zone route.** |
| `msf-companion/src/worker/index.ts` | Front door: forwards all traffic into the container |
| `msf-companion/src/app/api/health/route.ts` | Readiness probe the Worker polls on startup |
| `msf-companion/tsconfig.worker.json` | Typechecks the Worker separately from the app |
| `msf-companion/worker-configuration.d.ts` | Generated by `wrangler types`; committed |
| `infra/cloudflare/workflows/cloudflare-deploy.yml` | Validate on push; deploy on manual dispatch only. **Staged, not yet active** — see below |

### The deploy workflow is staged, not installed

`infra/cloudflare/workflows/cloudflare-deploy.yml` must be moved to
`.github/workflows/cloudflare-deploy.yml` before it will ever run. GitHub
refuses to let it be pushed into `.github/workflows/` from this environment:

- the credential with write access to `sccmavenger/ralph` lacks the `workflow`
  OAuth scope, and
- the credential that has `workflow` scope has no write access to this repo.

So this is a one-time manual step for someone with both:

```sh
git mv msf-companion/infra/cloudflare/workflows/cloudflare-deploy.yml \
       .github/workflows/cloudflare-deploy.yml
git commit -m "Install the Cloudflare deploy workflow"
git push
```

(Or create the file through the GitHub web UI, which carries the scope.)
Until then the file is inert — it is just text in the repo, which is exactly
why it is safe to have committed it here.

The production `Dockerfile` is used **unmodified**. That is the whole reason
Containers was chosen over the Workers/OpenNext adapter: `src/lib/youtube-pipeline.ts`
shells out via `node:child_process`, and `/api/cron/refresh-kb` and
`/api/admin/ingest` both import it. A Workers isolate cannot run that code.

### Deliberate safety properties

- **`wrangler.jsonc` has no `routes` key.** A deploy is reachable only at
  `*.workers.dev`. It is not possible for a deploy from this branch to take
  traffic for `themsftoolkit.com`.
- **The deploy job is `workflow_dispatch` + an explicit `deploy: true` input.**
  Pushing the branch or opening the PR does not deploy anything.
- **`enableInternet: true`.** The Cloudflare container template defaults this to
  `false`. Left at the default the app would come up but be unable to reach
  Stripe, Resend, Scopely OAuth, the MSF API or PostgreSQL — i.e. no sign-in and
  no payments, with a healthy-looking container.
- **`x-forwarded-host` / `x-forwarded-proto` are set from the edge request.**
  `src/app/api/auth/callback/route.ts` and `src/app/api/auth/refresh/route.ts`
  build their public base URL from those headers, falling back to the request
  host. The stock Cloudflare forwarding example rewrites the URL host to
  `container` and deletes the `host` header, which would redirect users to
  `https://container/...` on sign-in and token refresh.
- **The health route checks nothing but "Next.js is answering."** A database
  check there would make a slow dependency look like a failed container start
  and put the Worker into a restart loop.

### Instance sizing

Azure ran 0.5 vCPU / 1 GiB, `minReplicas: 1`, `maxReplicas: 3`, scaling at 50
concurrent requests.

The Worker starts a `standard-1` container (1/2 vCPU, 4 GiB, 8 GB disk), which
matches the Azure vCPU exactly and raises memory. Cloudflare bills **provisioned
memory and disk per second** but **CPU only when active**, so memory is the cost
driver:

- `standard-1` held warm 24/7 ≈ 4 GiB × 2.592 Ms × $0.0000025 ≈ **$26/mo**
  memory, plus ≈ $1.45/mo disk.
- `basic` (1/4 vCPU, 1 GiB, 4 GB) would be ≈ **$6.50/mo** memory + $0.73 disk,
  but halves CPU against Azure.

`INACTIVITY_TIMEOUT_MS` is 10 minutes, so an idle site is not billed for warm
memory — at the cost of a cold start on the next request. Azure's `minReplicas: 1`
had no cold start. Tune this against real traffic rather than guessing.

**A single container instance serves all traffic** (one Durable Object name,
`web`). This matches Azure's steady state of one replica but not its ability to
scale to three. Scaling out means routing across several Durable Object names,
which keeps each one warm and multiplies the memory bill — a Phase 2 decision to
take against measured load.

### Required Cloudflare credentials

Repository secrets:

- `CLOUDFLARE_API_TOKEN` — scoped to Workers Scripts:Edit, Containers:Edit,
  Workers Observability:Edit on the target account
- `CLOUDFLARE_ACCOUNT_ID`

Repository variable (optional, enables the post-deploy smoke test):

- `CLOUDFLARE_PREVIEW_URL` — the `*.workers.dev` hostname of the deployed Worker

Container runtime secrets are pushed by the `sync_secrets` input using
`wrangler secret bulk`. They mirror the `env` block of `infra/app/web.bicep`
plus `CRON_SECRET`, `YOUTUBE_API_KEY` and `RESEND_API_KEY`:

```
DATABASE_URL  MSF_API_KEY  SCOPELY_CLIENT_ID  SCOPELY_CLIENT_SECRET
SCOPELY_REDIRECT_URI  SESSION_SECRET  STRIPE_SECRET_KEY  STRIPE_WEBHOOK_SECRET
STRIPE_PRICE_ID  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY  AZURE_OPENAI_ENDPOINT
AZURE_OPENAI_KEY  AZURE_OPENAI_GPT4O_MINI_DEPLOYMENT  AZURE_AI_SEARCH_ENDPOINT
AZURE_AI_SEARCH_KEY  CRON_SECRET  YOUTUBE_API_KEY  RESEND_API_KEY
```

`APPLICATIONINSIGHTS_CONNECTION_STRING` is deliberately not forwarded;
telemetry moves to Workers Logs (`observability.enabled` in `wrangler.jsonc`).

`NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` is also inlined into the client bundle at
image build time by the `Dockerfile`. It is a publishable key, so this is not a
secret leak, but the build-time value and the runtime value must agree.

### Deploying Phase 1 (preview only)

1. Subscribe the account to **Workers Paid** — Containers are not available on
   the Free plan.
2. Set `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets.
3. Run **Cloudflare Web Deploy** → `workflow_dispatch` with `deploy: true` and
   `sync_secrets: true` on the first run.
4. Record the `*.workers.dev` hostname, set `CLOUDFLARE_PREVIEW_URL`, and
   confirm `/api/health` answers.
5. Run the Playwright e2e suite against the preview hostname. Note the warning in
   `msf-companion/AGENTS.md`: the default Playwright setup uses captured live
   credentials and its teardown kills the port-3000 listener. Use a test-owned
   configuration with dummy secrets.

Nothing above touches `themsftoolkit.com`.

## 3. Cutover (only after Phase 1 verifies)

Downtime budget: ~1 hour.

1. **Pre-flight.** Preview hostname healthy; e2e green; Postgres migrated off
   Azure and reachable from the container (`enableInternet: true`); secrets
   synced.
2. **Switch nameservers at GoDaddy** to `roxy.ns.cloudflare.com` and
   `theo.ns.cloudflare.com`. The zone goes `pending` → `active`. At this point
   traffic still reaches Azure, because the proxied root `A` record still points
   at `20.66.70.23`.
3. **Verify the zone is serving correctly off Azure** — full site, sign-in,
   checkout. This separates "DNS moved" from "hosting moved" so the two cannot
   fail together.
4. **Add the zone route** to `wrangler.jsonc` (`themsftoolkit.com/*` and
   `www.themsftoolkit.com/*`) and redeploy. This is the moment traffic moves to
   Cloudflare.
5. **Re-point webhooks**: Stripe and Resend. Re-verify their signing secrets.
6. **Confirm Scopely OAuth** redirect URI still matches `SCOPELY_REDIRECT_URI`.
7. **Confirm the scheduled jobs** still run — see §4.

### Rollback

- *Before step 4*: nothing to roll back; traffic is still on Azure.
- *After step 4*: remove the zone route and redeploy, or set the root `A` record
  back to `20.66.70.23` proxied. Azure must be kept warm and undeleted for this.
- *Full retreat*: set the GoDaddy nameservers back to `ns19`/`ns20.domaincontrol.com`.
  Allow for TTL propagation.

**Do not delete `rg-msf-companion-prod` until a full clean billing cycle has run
on Cloudflare.**

## 4. Scheduled work — correction to the original plan

The original plan proposed porting 18 Azure Function timer triggers to Workers
cron triggers. **That work is largely unnecessary.**

Per `AGENTS.md`, the Azure Function App is *stopped legacy infrastructure*.
Scheduled work actually runs through:

- `.github/workflows/refresh-kb.yml` on a GitHub Actions cron
  (`0 0,6,12,18 * * *`), which `POST`s to
  `https://themsftoolkit.com/api/cron/sync-gamedata` with a `CRON_SECRET`
  bearer token; and
- a dedicated self-hosted Windows runner labelled `msf-kb` for creator
  transcripts, which exists specifically because **YouTube blocks caption
  extraction from Azure-hosted IP ranges**.

Consequences for this migration:

- The GitHub Actions scheduler is host-agnostic. It keeps working after cutover
  with **no change**, as long as `CRON_SECRET` is set on the container and the
  `/api/cron/*` routes stay reachable. This is why `CRON_SECRET` is in the
  forwarded env list.
- The self-hosted `msf-kb` runner is **unaffected** by the migration — it is not
  Azure-hosted and does not call Azure. Do not try to move caption extraction
  into a Worker or a Cloudflare container: the same IP-reputation problem that
  made Azure unusable would very likely apply, and `yt-dlp` needs a real process.
- Web cron endpoints exist at `/api/cron/{email,refresh-kb,resolve-gaps,sync-gamedata}`.
  They are ordinary app routes and move with the container.
- Do **not** restart or migrate the stopped Function App as part of this work.

The remaining Phase 2 question is therefore much smaller than the plan assumed:
confirm which of the 18 timers are genuinely dead, and whether any surviving
schedule is missing from `refresh-kb.yml`.

This is a data migration with a correctness risk, not a hosting change.
